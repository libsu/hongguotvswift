# 红果 TV 前端交互体验优化方案

> 目标：解决两大类最直观的体验问题——
> 1. **点击切换要等网络**（点卡片后原地转圈，画面不切换）；
> 2. **图片素材不缓存、无请求队列**（榜单 100 张封面同时请求，无磁盘缓存）。

---

## 一、问题总览

| # | 体验问题 | 用户可感知的表现 | 代码根因 | 涉及文件 |
|---|---------|----------------|---------|---------|
| A | 点击卡片要等网络才切画面 | 点了卡片 → 原地 `ProgressView` 转圈 → 详情请求回来后画面才跳 | `open()` 先停旧播放、发起 `detail` 网络请求，**网络返回后才 `showDetail = true`**；`perform()` 一开始就把 `busy = true`，整页进入"加载态"并置灰卡片 | `Sources/HongguoMac.swift`、`Sources/GUI/ContentView.swift` |
| B | 图片无磁盘缓存、无请求队列 | 每进一次榜单重新下载 100 张封面；滚动时 100 张图同时抢带宽 | 所有封面都用系统 `AsyncImage`（无磁盘持久缓存、无并发/队列控制），**已实现的 `CoverCache`/`CoverImageView`（磁盘+内存缓存）根本没有被接入** | `Sources/GUI/ContentView.swift`、`Sources/GUI/HomeViews.swift`、`Sources/GUI/PlayerView.swift`、`Sources/tvOS/TVComponents.swift`、`Sources/GUI/CoverImage.swift` |

## 二、核心概念厘清

### 「点击切换等待」 vs 「点击等待切换」

这是本次优化的总纲。两种时序的本质区别：

```
❌ 现状「点击 → 等待 → 切换」：
   点击 → 详情网络请求（阻塞）→ 请求完成 → 切换 UI
   ⬇ 用户观感：点了没反应，画面卡住 + 转圈

✅ 目标「点击 → 切换 → 等待」：
   点击 → 立即切换 UI（先展示占位/骨架/缓存的旧数据）→ 后台请求 → 数据到达后填充
   ⬇ 用户观感：点了立刻有反应，内容按区域逐步填充
```

**核心原则：任何用户手势都应先给出即时、确定的视觉反馈（切换状态 / 占位骨架），网络加载永远在"后台"进行，不与导航锁死。**

## 三、问题 A：点击切换要等网络

### 3.1 根因拆解

`Model.open(_:trial:resumeEpisodeID:resumePosition:)`（`HongguoMac.swift` 约 300 行）的当前时序：

1. `perform { ... }` → `busy = true`（整页进入加载态，卡片被置灰 / 列表显示转圈）。
2. 立即 `saveProgress()` + `player.pause()` + `replaceCurrentItem(with: nil)`（旧节目现场被清空，画面变黑）。
3. `let detail = try await self.request("detail", ...)` —— **阻塞在网络请求上**。
4. 请求返回后才执行 `self.detail = detail; self.showDetail = true`。

问题在于第 3 步与第 4 步之间：**UI 切换（`showDetail = true`）被网络请求卡在门后**。而 `perform` 又同时把 `busy` 设为 true，进一步把「等待」放大成整页转圈 + 禁用交互。

另外 `ContentView.card`（`ContentView.swift` 约 196 行）点击动作是：

```swift
Button {
    if cloud?.online == false { model.message = "..." }
    else { model.open(series, trial: model.section == "推荐") }
} label: { ... }
```

点击后只有 `open` 内部的状态变化，而 `open` 的可见状态变化被网络请求延后了。

### 3.2 为什么不能简单「先 open 完再 showDetail」

原因是 `Detail` 数据（集数列表、封面、简介）目前**只有网络请求返回后才存在**，没有任何本地兜底，所以无法在请求前渲染详情页。因此切换必须建立在「有东西可先渲染」的基础上。

### 3.3 优化方案（分层，按收益从高到低）

#### 方案 1：先切详情骨架，再后台填数据（推荐，收益最大）

把 `open()` 拆成「切换」与「填充」两个阶段：

1. **同步阶段（立即执行，不 await）**：
   - `self.showDetail = true`（立刻切到详情容器）。
   - 设置一个「加载中」的 `Detail` 占位（只含 `series` 的 id/title/cover/description，episodes 为空）。
   - 停旧播放、清相关面板（comments/danmaku 等）。
   - **不要**把 `busy` 置为 true（详情加载属于详情页内部的局部 loading，不该锁死全局）。

2. **异步阶段（后台填充）**：
   - 用独立 `Task`（或带 `generation` 的请求令牌）去拉 `detail`。
   - 返回后校验 `generation`（防止用户连续点两个卡片导致旧响应覆盖新响应），再填充 `self.detail`。
   - `episode` 选择、`related` 拉取、云端续播判断全部挂在「detail 到达后」。

> 这样用户点卡片后，画面**立刻**从列表/首页切到详情页（哪怕先看到标题和骨架），网络返回后集数列表、相关作品等逐块亮起。

#### 方案 2：回收 `busy` 的滥用，把「全局繁忙」拆成「局部加载」

现在 `busy` 有一刀切语义（`perform` 一进入就 true），导致：

- 点卡片 loading 时，**整个榜单列表被置灰 + 显示转圈**（`ContentView` 第 47 行的 `if model.busy || model.cloudLoading { ProgressView() }`）。
- `AccountPanel`、`HomeFeedView` 等多个按钮 `.disabled(model.busy)` 被连带禁用。

建议：

| 现状 | 建议 |
|------|------|
| `busy` 同时表示「全局导航加载中」和「局部详情/分页加载中」 | 分层：`busy` 只表示**首屏骨架 / 全页级**加载；详情加载、分页加载、图片加载各有独立状态 |
| 加载期间整个列表被 `ProgressView` 覆盖 | 改为**骨架屏（skeleton）**或局部 spinner，列表骨架保持在位、可继续滚动 |
| 卡片被 `.disabled(model.busy)` 置灰 | 仅在真正需要互斥时禁用（如正在提交），加载期间保持可点、可快速切换 |

#### 方案 3：详情请求加本地缓存 + 乐观回填

给 `detail` 加一层类似 `CatalogCache` 的磁盘缓存（键：`series.id`）。点击时先读缓存立即渲染，再后台刷新。这样：

- 二次进入同一部剧，详情页**秒开**（第一集列表立即可见、可点）。
- 首次进入也有骨架兜底。

> 这与问题 B 的图片缓存属于同一套「先本地、后网络」的思路，可共用磁盘缓存目录策略。

### 3.4 连续快速点击的竞态保护

拆成「先切后填」后，必须处理用户连续点 A、B 两部剧的场景：

- 用一个 `detailGeneration = UUID()`（或请求令牌），每次 `open` 时递增。
- 详情请求回来时校验 `detailGeneration == 当前代`，否则丢弃（否则会出现 B 的画面被 A 的晚到响应覆盖）。
- 现有代码里 `perform` 内部的 `generation` + `performGeneration` 已具备类似能力，只需把「切换」与「填充」解耦后沿用同一套令牌即可。

## 四、问题 B：图片不缓存、无请求队列

### 4.1 根因拆解

项目里两张图加载路径：

| 组件 | 是否被使用 | 缓存能力 |
|------|-----------|---------|
| 系统 `AsyncImage` | **几乎全部封面都在用它** | 仅 SwiftUI 内存级（URLCache 默认），**无磁盘持久缓存**，下次进入/重启后重新下载 |
| `CoverImageView` + `CoverCache`（`CoverImage.swift`） | **定义了但从未被任何视图引用** | 内存（`NSCache`，countLimit 256）+ 磁盘（`applicationSupportDirectory/HongguoTVMac/covers`，上限 1000 文件），完全符合需求，却未接线 |

封面图使用点（均需改造）：

- `GUI/ContentView.swift` → `card(_:)` 的封面（榜单/找剧/搜索列表主页卡）
- `GUI/HomeViews.swift` → `seriesCard` / `historyCard` / `cloudCard`
- `GUI/PlayerView.swift` → 相关作品卡片
- `tvOS/TVComponents.swift` → `TVCoverImage`（tvOS 侧也同病相怜）
- `GUI/CommentsPanel.swift` → 头像（可另用头像专用缓存或共用封面缓存键）

**问题 B 的完整症状：**

1. 「榜单 100 部剧 = 100 张封面」，`List`/`LazyVGrid` 的懒加载**只保证不渲染屏幕外的视图**，但对**已渲染但仍在可视区附近**的封面，`AsyncImage` 会**同时**发起全部下载请求，没有并发上限、没有优先级、没有队列。
2. `AsyncImage` 落的内存缓存是系统 URLCache，**不做长期/磁盘持久化**，下次进入或重启后 100 张重新下载。
3. 无「只加载可视区 + 预取邻近区」的队列策略，带宽被榜单整页首屏一次性打满，滚动时还在抢。

### 4.2 优化方案（按收益排序）

#### 方案 1：把 `CoverImageView` 接入到所有封面（最重要，改动小收益大）

`CoverImage.swift` 里的 `CoverImageView` 已经实现了磁盘 + 内存双层缓存，**只需把各视图里的 `AsyncImage(...)` 全部替换为 `CoverImageView(urlString:)`**。

示例（`ContentView.card`）：

```swift
// 改前
AsyncImage(url: URL(string: series.cover)) { image in image.resizable().scaledToFill() }
    placeholder: { Rectangle().fill(.gray.opacity(0.18)) ... }
    .frame(height: 225)...

// 改后
CoverImageView(urlString: series.cover)
    .frame(height: 225).frame(maxWidth: .infinity).clipped().cornerRadius(10)
```

`CoverImageView` 内部已处理：磁盘命中 → 内存命中 → `URLSession` 下载 → 写磁盘 + 写内存，`task(id:)` 确保 URL 变化时重载。

**这一步直接解决「下次点击/进入又加载 100 张」的问题**（磁盘缓存命中，二次进入几乎 0 网络），是四项改造里性价比最高的。

#### 方案 2：给图片加载加「可见性驱动 + 并发上限」队列

现状 `CoverImageView.load()` 里 `URLSession.shared.data(from:)` 是**无界并发**的。方案：

- 在 `CoverCache` 内**增加一个并发受限的下载队列**（例如 `actor` + 信号量，上限 4～6 个并发）。
- 结合 SwiftUI `onAppear`/`onDisappear`（或 `LazyVGrid` 的懒加载天然提供的可见性），只对**进入可视区**的卡片触发加载；滚出可视区时取消未完成的下载（`CoverImageView` 已用 `task(id:)` 支持取消，补齐取消后移除队列占位即可）。
- 对「榜单顶部前 10 项」给予更高优先级（可见区优先），其余按滚动顺序排队。

这样把「100 张同时请求」收敛为「可视区先加载 + 邻近区排队预取」，带宽平顺、首屏更快。

#### 方案 3：URLSession 缓存策略与图片降采样

- 封面通常只需渲染到卡片尺寸（如 200～300pt），但源图可能是原尺寸高清图。可在下载后按目标尺寸做**降采样/缩略图**再写磁盘，进一步减小体积、加快命中后的内存解码。
- 给 `CoverCache` 的磁盘键增加内容长度/大小上限校验（当前已限制了文件数，但单文件大小未限）。

#### 方案 4：tvOS 侧同步改造

tvOS 的 `TVCoverImage`（`TVComponents.swift`）同样直接 `AsyncImage`。tvOS 需要自己的磁盘缓存目录（`cachesDirectory` 或 `applicationSupportDirectory`），可复用 `CoverCache` 的键设计（SHA-256）与队列逻辑，将 `TVCoverImage` 换成受控缓存实现。

## 五、改造建议的落地顺序与影响面

| 阶段 | 改动 | 影响文件 | 风险 / 备注 |
|------|------|---------|-----------|
| **1（推荐先做）** | 全项目把封面 `AsyncImage` → `CoverImageView` | `ContentView.swift`、`HomeViews.swift`、`PlayerView.swift`、`TVComponents.swift` | 低风险，纯视图替换；`CoverImageView` 已存在，无需新造轮子 |
| **2** | `open()` 拆成「先切详情骨架 + 后台填充」，解除 `busy` 与导航的锁死 | `HongguoMac.swift` | 中风险，需处理竞态令牌；是体验 A 的关键 |
| **3** | 引入「局部加载态」替代全局 `busy`（骨架屏/局部 spinner） | `ContentView.swift`、`HomeViews.swift`、`AccountPanel.swift` 等 | 中风险，涉及多个视图的 loading 分支 |
| **4** | 图片下载队列（并发上限 + 可见性优先级） | `CoverImage.swift` | 中风险，需 `actor`/信号量与取消联动 |
| **5（可选锦上添花）** | 详情本地缓存 + 乐观回填 | `HongguoMac.swift`、新增缓存类 | 低风险，复用 `CatalogCache` 模式 |

> 建议按阶段 1、2、3 的优先级推进：阶段 1 立刻消除「重进重复下载 100 张图」；阶段 2 立刻消除「点击卡顿转圈」；阶段 3 把「转圈」进一步软化为骨架，让等待更自然。

## 六、验收标准（回归重点）

优化后应满足：

1. **点击反应**：点击任意剧卡片，画面**立即**切换到详情页（骨架/本地缓存优先），网络只决定内容何时填充，不再决定画面何时切换。
2. **不再全局转圈**：点击详情加载期间，标题栏不出现整页 `ProgressView`，列表/首页可继续操作；`busy` 不再把无关按钮连带禁用。
3. **图片二次进入**：进入一次榜单后退出再进入，封面**立即显示**（磁盘缓存命中），不重新请求 100 张。
4. **请求收敛**：榜单首屏只请求可视区 + 邻近区封面的并发（受上限约束），滚动加载而非一次性 100 张并发。
5. **竞态安全**：连续快速点击 A、B 两部剧，最终停留在 B 的详情与数据一致，不出现 A 晚到覆盖 B 的画面。
